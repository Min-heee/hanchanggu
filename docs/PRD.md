# 한창구 PRD

> 이 문서는 **구현을 시작하기 전에** 썼습니다. 저장소의 첫 커밋은 코드가 아니라 이 문서입니다. 초안은 Claude Code가 조사 5건(문의 창구 전수 조사, 메신저 API, 비메신저 API, 기존 상담 도구, 법·약관·개인정보)을 바탕으로 썼고, 채택 여부와 7절 기준값은 제 몫입니다. 확인한 사실에는 근거를, 추론에는 [추론]을, 확인하지 못한 것에는 "미확인"을 붙였습니다.

## 1. 한 줄 정의와 문제

**한창구는 병원의 여러 문의 창구에서 들어온 문의를 한 목록에 모으고, 병원이 승인한 문서만 근거로 답장 초안을 만들어 직원이 검토한 뒤 보내게 하는 AI 업무 코파일럿입니다. 같은 문서와 같은 엔진으로 직원의 내부 질문에도 근거를 달아 답합니다.**

동네 의원도 환자와 고객이 문의를 넣을 수 있는 창구가 많습니다. 메신저(카카오톡 채널, 네이버 톡톡, 인스타그램 DM), 홈페이지 폼, 네이버 예약 요청사항, 전화·문자, 플레이스 리뷰, 유튜브 댓글, 블로그·카페, 쇼핑몰 문의가 흩어져 있고, 한 사람이 여러 창구를 함께 맡는 경우가 흔합니다[추론].

여기서 세 가지 문제가 생깁니다[추론].

1. **놓칩니다.** 창구마다 따로 열어 봐야 해서, 쉬는 날과 밤사이 쌓인 문의 중 무엇이 먼저인지 알기 어렵습니다.
2. **같은 답을 매번 새로 씁니다.** 수술 후 며칠째 무엇을 해도 되는지, 가격, 예약 변경 규정처럼 답은 병원 문서에 이미 있지만 사람이 찾아서 옮겨 적습니다.
3. **답하면 안 되는 문의가 섞여 있습니다.** "수술 9일째인데 고름이 나와요" 같은 증상 문의에 비의료인이 판단해 답하면 위험하고, 의료법상 문제가 될 수 있습니다.

한창구는 이 셋을 한 화면에서 다룹니다. 목록이 우선순위를 정하고, 적신호는 AI보다 규칙이 먼저 잡아 의료진에게 넘기고, 나머지는 병원 문서의 어느 문장을 근거로 썼는지 보이는 초안으로 만듭니다. **보내는 것은 언제나 사람입니다.**

## 2. 목표와 비목표

### 목표

- 여러 창구의 문의를 창구 배지, 받은 시각, 기다린 시간, 상태(새 문의 / 초안 / 인계 / 보류 / 발송)와 함께 한 목록에 보인다.
- 문의 유형과 우선순위를 분류하고, 왜 그렇게 분류했는지 근거 표현을 함께 보인다.
- 증상 적신호는 LLM보다 앞선 규칙이 먼저 잡아 의료진 인계 카드로 넘긴다. 애매하면 인계한다.
- 답장 초안은 **① 검색 → ② 발췌 → ③ 생성 → ④ 근거 표시** 네 단계를 화면에 그대로 보여 주고, 문장마다 병원 문서의 원문 위치를 단다.
- 같은 엔진으로 직원이 묻는 내부 질문에 답한다(사내 Q&A).
- 사람이 만든 골든셋으로 검색 적중률, 인용 정확도, 보류, 적신호 누락을 재고 결과를 README에 그대로 싣는다.
- API 키 없이도 링크 하나로 30초 안에 위 흐름을 본다(미리 생성한 응답을 쓰는 시연 모드).

### 비목표

- **진단, 치료 판단, 약 용량, 효과 보장, 탈모 단계 판정.** 이런 답은 생성하지 않고 "의료진 확인 필요"로 넘깁니다.
- **실제 채널 연결.** 조사 결과 카카오톡 채널 1:1은 공식 딜러사를 거쳐야 하고, 인스타그램 DM은 사업자 인증과 고급 권한 심사가 필요하며, 네이버 톡톡은 파트너 검수 뒤에만 열리고, 네이버 예약·리뷰·블로그는 공개 API가 없습니다(6절). 그래서 공통 어댑터 형식만 만들고 입력은 합성 데이터로 합니다.
- 자동 발송, 창구가 다른 사람을 같은 환자로 자동 병합하기, 진료기록 연동, 로그인, 실제 병원 데이터.

## 3. 사용자와 시나리오

**사용자 A — CS 직원(주 사용자).** 휴무 다음 날 아침 10시에 출근해 한창구를 엽니다. 쉬는 동안 쌓인 문의 30건이 창구와 상관없이 한 목록에 있습니다. 맨 위 빨간 칸은 적신호 인계 1건이고, 그 아래 주황 칸은 예약금을 냈는데 확정 연락을 아직 못 한 건입니다. 가격 문의 하나를 열면 초안이 준비돼 있고, 문장마다 작은 번호가 붙어 있습니다. 번호를 누르면 옆에 병원 문서 원문이 열리고 해당 문장이 칠해져 있습니다. 가격은 AI가 쓴 숫자가 아니라 가격표에서 그대로 들어온 값입니다. 한 문장을 고치고 승인하면 발송 기록이 남습니다.

**사용자 B — 원장·간호(인계 카드).** 인계 카드에는 문의 원문, 어떤 규칙이 걸렸는지("수술 후 문맥 + '고름'·'열'"), 환자가 스스로 적은 수술 후 일수가 있습니다. 한창구는 증상을 해석하지 않습니다.

**사용자 C — 신입 직원(사내 Q&A).** "수술 3일째 환자가 머리를 감아도 되냐고 물으면 뭐라고 해요?"를 묻습니다. 답과 함께 근거 문서가 뜨고, 근거가 없는 질문("주차 정산은요?")에는 "승인된 문서에 없습니다"라고 답하며 그 질문을 '문서 빈칸' 목록에 쌓습니다.

**사용자 D — 채용 심사자(노트북, API 키 없음).** 링크를 열면 시연 모드로 들어갑니다. 합성 문의 목록, 적신호 인계, 인용 달린 초안, ①~④ 단계 표시, 평가 탭까지 30초 안에 봅니다. 화면에는 "가상 의원 · 합성 데이터 · 미리 생성한 AI 응답"이 항상 표시됩니다.

A~C는 가정한 사용자입니다. 병원 현장 인터뷰나 검증은 하지 않았습니다.

## 4. 요구사항

| ID | 무엇을 | 왜 | 완료 기준 |
|---|---|---|---|
| F1 | 합성 데이터: 가상 의원 문서 볼트(Obsidian에서 바로 열리는 md 20편 안팎, 프런트매터에 유형·버전·승인 상태·시행일), 합성 문의 40건(창구 8종 이상, 손으로 쓴 적대 케이스 포함), 골든셋 50문항 | 실제 환자 데이터를 쓰지 않는다. 평가 정답은 사람이 적는다 | 볼트를 Obsidian으로 열면 링크가 이어진다. 골든셋 문항마다 정답 문서 ID와 "보류해야 함" 여부가 사람이 적은 값으로 있다 |
| F2 | 창구 어댑터: 공통 문의 형식(창구, 외부 ID, 받은 시각, 가명 작성자, 본문, 첨부 메타, **답장 방식**: 직접 / 복사 / 전화 / 고정 문구만) | 어떤 상담 도구나 웹훅이 와도 같은 형식으로 받는다 | 창구별 답장 방식 표가 데이터로 있고, 화면의 발송 버튼이 그 방식을 따른다 |
| F3 | 통합 목록 | 놓치지 않게 | 적신호 → 예약 확정 대기 → 오래 기다린 순으로 정렬되고, 창구·유형·상태로 거를 수 있다 |
| F4 | 분류(유형·우선순위) | 무엇부터 볼지 | 분류마다 근거 표현이 붙는다. 모델 호출이 실패하면 "미분류"로 남고 기본값을 채우지 않는다 |

| F6 | ① 검색·② 발췌 | 근거가 될 문단을 찾는다 | 한국어 n-gram BM25로 문단 단위 검색, **승인된 최신 버전만** 대상. 제외된 문서(미승인, 옛 버전)는 "제외됨"으로 화면에 보인다 |
| F7 | ③ 생성·④ 근거 | 문장마다 출처 | Claude API의 문서 인용(citations)으로 생성한다. 인용된 문장이 원문에 실제로 있는지 코드가 다시 대조하고, 어긋나면 보류한다. 인사·맺음말을 뺀 무인용 문장은 막는다 |
| F8 | 고정값 삽입 | 가격·진료시간 환각 방지 | 가격과 진료시간은 모델이 쓰지 않고 볼트의 가격표·안내 문서에서 템플릿으로 들어간다 |

| F11 | 공개 창구 규칙 | 공개 답글이 그 사람이 환자라는 사실을 드러내지 않게 | 리뷰·유튜브 댓글에는 치료 내용이 없는 고정 문구만 제안한다 |
| F12 | 승인·발송(모의)·기록 | 사람이 보낸다 | 누가 언제 어떤 문장을 고쳤는지 남는다. 실제 전송은 없다 |
| F13 | 사내 Q&A | 공고의 "사내 지식 시스템" | 문의 초안과 같은 ①~④ 엔진을 쓴다. 근거 없는 질문은 '문서 빈칸' 목록에 쌓인다 |
| F14 | 평가 탭 | 주장 대신 숫자 | 7절 지표를 골든셋으로 계산해 보이고, 틀린 사례도 목록으로 보인다 |

## 5. 파이프라인

```
문의 → 가림(F9) → 적신호 게이트(F5, 규칙) ─┬─ 인계 카드
                                            ├─ 공개 창구 → 고정 문구(F11)
                                            └─ 분류(F4) → ① 검색 → ② 발췌 → ③ 생성 → ④ 근거·검증(F7, F8, F10) → 직원 승인(F12)
```

- **검색은 임베딩 없이 BM25로 시작합니다.** 문서 20편, 문단 수백 개 규모이고, "D+3", "모당"처럼 정확히 맞아야 하는 용어가 많습니다. 결과를 사람이 설명할 수 있다는 장점도 있습니다. 문서가 수천 편으로 늘면 임베딩을 섞는 하이브리드로 바꿉니다.
- **인용은 프롬프트로 부탁하지 않고 API 기능으로 받습니다.** 문서 인용 기능은 원문 위치를 돌려주므로 코드가 검증할 수 있습니다. 이 기능은 구조화 출력과 한 호출에 함께 쓸 수 없어서, 분류(구조화 출력)와 생성(인용)은 따로 부릅니다.
- **모델.** 기본은 `claude-opus-5`(적응형 사고)입니다. 거절 시 서버 측 대체 모델 기능을 켭니다. 더 싼 모델로 바꿀지는 비용을 재 본 뒤 제가 정합니다.
- **문의 원문은 데이터로만 다룹니다.** 문의에 "이전 지시를 무시하고…" 같은 문장이 들어와도 지시로 따르지 않게 시스템 지시와 분리하고, 이런 문의를 적대 케이스에 넣습니다.

## 6. 설계 결정과 대안

**왜 채널을 직접 연결하지 않는가.** 조사한 결과는 이렇습니다(2026-09 기준, 상세는 비공개 조사 노트).

| 창구 | 외부 도구로 받기 | 외부 도구에서 답장 |
|---|---|---|
| 카카오톡 채널 1:1 | 상담톡(공식 딜러 경유)만 | 상담톡만 |
| 네이버 톡톡 | 챗봇 API(파트너 검수 뒤) | 가능 |
| 인스타그램 DM | 메시징 API(사업자 인증·권한 심사) | 24시간 안, 조건부 |
| 홈페이지 폼 | 알림 메일, 제작 도구 API | 불가(전화로 답) |
| 네이버 예약 요청사항 | 공개 API 없음, 알림 메일 | 불가 |
| 리뷰·블로그·카페 | 공개 API 없음 | 불가 |
| 유튜브 댓글 | 공식 API(본인 채널) | 가능 |

**"채널톡 같은 상담 도구를 쓰면 되지 않나요?"** 메신저를 한곳에 모으는 일은 그런 도구가 이미 잘합니다. 한창구는 그 옆에 붙는 층입니다. 메신저는 상담 도구가 받고, 상담 도구가 받지 못하는 창구(예약 요청사항, 문자, 폼, 리뷰, 댓글)와 **병원 규칙**(적신호 인계, 승인 문서 근거, 가격 템플릿, 공개 창구 규칙)은 한창구가 붙입니다. 어댑터(F2)는 특정 도구에 묶이지 않습니다.

**왜 AI가 보내지 않는가.** 증상·진료에 관한 답은 의료인의 몫이고, 답장에 섞인 광고성 표현은 규정 문제가 됩니다. 초안까지만 AI가 쓰고, 보내는 결정은 사람이 합니다.

**왜 같은 사람을 자동으로 합치지 않는가.** 잘못 합치면 다른 환자의 치료 정보가 초안에 들어가 그대로 유출됩니다. 직원이 확인했을 때만 연결합니다. 치료 단계(수술 후 며칠째)는 환자가 문의에 쓴 문장에서 읽거나 직원이 입력한 값만 씁니다.

**왜 합성 데이터인가.** 문의에는 증상과 사진 같은 건강 정보가 섞여 있어 민감정보일 가능성이 높습니다[추론]. 공개 저장소와 시연에는 가상 의원('샘플의원')의 문서와 사람이 쓴 합성 문의만 넣고, 실제 후기·대화를 바꿔 쓴 문장도 넣지 않습니다.

**스택.** Next.js 15(App Router, 서버 라우트), TypeScript, `@anthropic-ai/sdk`, vitest, Vercel. 합성 데이터 규모에서는 데이터베이스 없이 저장소의 JSON과 마크다운으로 충분합니다. 승인·발송 기록은 시연 동안 브라우저에만 남습니다.

## 7. 성공 지표와 평가(사전 기준)

기준은 미리 적고, 못 미쳐도 결과를 그대로 싣습니다. 정답은 사람이 적은 값이고, 모델의 답을 같은 모델로 채점하지 않습니다.

- **적신호 누락 0건.** 손으로 쓴 적신호 문의 15건 기준입니다. 규칙이 애매하면 인계하므로 과잉 인계는 허용하고, 그 비율은 따로 적습니다.
- **잘못된 인용이 초안에 남는 경우 0건.** 인용 검증에 실패하면 보류로 떨어지게 만들었으므로, 이 숫자가 0이 아니면 검증 코드의 결함입니다.
- **검색 적중률 90% 이상.** 골든셋 정답 문서가 상위 5개 안에 드는 비율입니다.
- **보류 정확도 90% 이상.** 근거가 없는 질문을 보류하고, 근거가 있는 질문은 보류하지 않는 비율입니다.
- **테스트가 결함을 잡는지 확인.** 일부러 결함을 심은 변이(승인 필터 빼기, 인용 대조 빼기, 규칙 인계를 LLM이 풀게 하기, 가림 빼기)를 넣고 테스트가 실패하는지 봅니다. 살아남은 변이도 README에 싣습니다.

## 8. AI 코딩 툴 사용 방식

이 프로젝트는 Claude Code를 중심으로 만듭니다. 사실대로 나누면 다음과 같습니다.

| 구분 | 내용 |
|---|---|
| AI(Claude Code)가 한 것·할 것 | 조사 5건, 이 PRD 초안, 가상 의원 문서·합성 문의·골든셋의 초안, 코드와 테스트 초안, 적대적 검토 |
| 사람(제)이 하는 것 | 아이디어(여러 창구 문의를 한 번에 보고 답장하는 도구), 초안의 채택·수정·거부, 골든셋 정답 검수, 7절 기준값 확정, 모델·비용 결정, 최종 문장에 대한 책임 |
| 검증 | 출처가 있는 문장만 사실로 적는다. 평가 정답은 사람이 검수한다. 확인하지 못한 것은 "미확인"으로 남긴다 |

> **구현 후 갱신 예정:** AI가 틀렸던 지점, 제가 되돌린 결정, 실제 비용을 표로 기록합니다.

## 9. 리스크와 남은 일

- **외부 API로 건강 정보가 나간다.** 실제 병원에서 쓴다면 가림만으로는 부족합니다. 처리 위탁·국외 이전 고지, 동의, 학습 미사용 설정, 보관 기간 정책이 먼저이고, 민감한 문의는 원내 모델로 처리하는 대안도 검토해야 합니다. 이 데모는 그 검토를 대신하지 않으며, 법률 자문이 아닙니다.
- **AI 답변 고지.** 고객에게 나가는 글에 AI가 관여했다는 사실을 어떻게 알릴지는 병원 정책과 법 검토가 필요합니다. 데모 화면에는 "AI 초안, 사람이 검토 후 발송"을 항상 표시합니다.
- **환각.** 인용 검증과 무인용 문장 차단, 가격 템플릿으로 줄이지만 0으로 만들지는 못합니다. 그래서 사람이 보냅니다.
- **프롬프트 인젝션.** 문의 원문에 지시문이 섞일 수 있습니다. 적대 케이스로 확인합니다.
- **운영 주체가 다른 데이터.** 병원과 쇼핑몰이 서로 다른 사업자라면 문의를 한 저장소에 합칠 수 없습니다. 실제 도입 전에 확인해야 합니다[추론].
- **일정.** 구현 가능 기간이 5일입니다. 자르는 순서는 평가 탭의 세부 → 광고 표현 검사 → 공개 창구 규칙 → 사내 Q&A 화면 분리입니다. 적신호 게이트와 인용 검증은 자르지 않습니다.
